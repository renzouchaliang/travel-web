版本：1.0.0 审阅稿 · 2026-10-04。对应 `travel-handoff.schema.json`、`template-contract.json` 与已确认模板 `travel-template-v1-r13`。样式基准 Git 提交：`b12af99a2bb6b84ca7cbc2296a838d27735a36d5`。

## 2. 日常交接只需一份 JSON，不上传图片

方案完成后返回 `trip-<旅行id>.json`，符合 Schema。所有景点图片、探索候选图和每日头图使用网上可直接加载的 http(s) 图片地址，不要求图片附件、不要求生成背景图、不要求手机解压或改代码。题诗是 JSON 内的文字。

优先选稳定、可引用的公开图片源。`src` 应是图片资源地址，不是攻略页面、图片搜索结果页、需登录或短时签名地址；同时记录来源页面。采集端检查链接可用性和图片内容是否对应地点。图片公开可查看不等于任何网站都允许外链；不把“网页中有图”当作已核实可用图片。

网页默认引用提供的 URL，不在发布阶段重新找图。景点及探索图片失败则隐藏／回到文字布局；缺少头图时用当天纯色，图片无法加载时至少保留底色和文字。不在正文显示图片来源和核查元数据。需要纠正失效链接时，由资料阶段更新 JSON，而不是发布智能体临时选替代图。

## 3. 聊天过程：先规划、后逐项补齐

先了解目的、日期、人数、同行人特点、预算、住宿、节奏、偏好和往返方式。用自然聊天给建议，逐步确认，不一次抛出全字段问卷。维护已确认方案与未决定事项，不能把建议直接变成已决定行程。

确认大框架后，按天确定地点、访问顺序、停留时间、通勤方式及主要约束。再分批查询景点事实、交通、餐饮、探索候选、图片、每日主题色和题诗。最终总结方案让用户确认，之后导出 JSON；如用户已明确授权确认，不反复要求同一项确认。

“重要采集目标”不等于每项都是阻止发布的字段。查询不到的图片、诗、购票链接、评分、距离等可缺失；缺失不能写为0、随便编一条或反复塞进旅行正文“待确认”。向用户报告资料缺口放在规划对话里，不放在面向同行人的网页里。

## 4. 根对象与版本

根对象是 `formatVersion`、`templateVersion`、`handoffStatus`、`publishAction`、`trip`，不要把根对象包装为另一种格式。`formatVersion` 固定 `1.0.0`，`templateVersion` 固定 `travel-template-v1-r13`。

`handoffStatus` 为 `draft`（仍在讨论）、`ready`（已确定并交付发布）或 `reference`（示例）。空白模板用 draft，长沙样例用 reference，发布输入必须 ready。Schema 通过不等于事实已经查实，也不等于旅行合理；这些判断必须在前期资料阶段完成。

未知可选字段省略；数组无内容用 `[]`，`places` 无地点用 `{}`，不要使用 null。所有 ID 稳定、全局唯一；`places` 的键必须等于该地点的 id。来源、照片、外链、天、停留、路段、餐饮分区的 ID 也不能互相重复。

`trip.days` 按日期排列；页头总天数取数组长度，起止日期从各日 date 推导。`trip.timezone` 写 IANA 时区，例如 Asia/Shanghai，时间以当地计划时间为准。

### 一套模板，多份旅行，各自链接

旅行ID代表一次旅行，不只代表城市。例如 `changsha-2026-10`、`beijing-2027-05`；同一城市不同次旅行也使用不同ID。Trip.id采用小写英文/拼音、数字和连字符，不用中文、空格或斜杠。

- `publishAction: "create"`：新增该ID的资料及注册项，保留已发布旅行。URL为现有域名加 `?trip=<id>`；也支持 `/trips/<id>`。它们共用一个网站部署，但属于不同攻略页。
- `publishAction: "update"`：明确更新同一个ID，保留原链接，新内容替换该旅行内容；不得影响其他旅行。
- 同一对话提交两份不同ID的create文件，分别校验、分别注册、返回两条不同链接；也可在新对话提交。聊天窗口不是旅行身份标识。
- create撞已有ID时，必须报告冲突，不自行覆盖、不自行改ID后悄悄发布；update找不到已有ID时也报告问题。用户需明确这是新旅行还是更新。
- 新Cloud Codex对话选择同一GitHub仓库，读取本目录规范并接收JSON即可，不必重新说明样式。若换了仓库或部署账号，先定位原项目；不能假定新窗口自动继承项目权限和地图配置。


## 5. 地点库与每日访问分开

`trip.places` 保存物理地点，不重复创建同一家酒店。一次访问用一个 Stop；同酒店早出晚归可有多个 Stop，placeId 相同、stop id 不同。餐馆、景点、酒店、机场、车站、其他地点都用 Place。

`Place.name` 保留完整名称，餐馆完整分店名称不要丢失；`mapLabel` 写显示短名，餐饮标题只显示店名，不含括号内分店，不再追加 branchName。地址、坐标、门店链接继续识别准确分店；同品牌不同店不能因为标题相同而合并。

采集地点简介、适用开放/门票/预约事实、开放时间节点、照片和外链。缺项直接省略。不要给酒店和车站强填景点照片，不把攻略链接当成购票链接。

## 6. 日程卡片与交通卡片

Day.stops 按访问顺序排列，记录时间、计划停留、说明、目的和对应地点。role 用 main、optional 或 free-time；visitPurpose 区分游览、拍照、场馆、公园、自由活动。

Day.legs 是相邻或明确连接两个停留点的独立通勤卡片：fromStopId、toStopId 都引用该日 Stop，起点必须排在终点前面。填写 mode、可执行 summary、方向、上车、下车、出口及有依据的用时。公共交通写明线路、乘车方向、上下车站、出口；lineColor 与当地线路配色匹配。

交通 mode 仅有 walk、transit、drive、taxi、cycle。本地地铁/公交用 transit，公交需要两端 Place.providerIds.amapCity。实际规划入口可用 routingFromPlaceId / routingToPlaceId，例如书院入口或地铁站；它们不能让探索图层自动显示。

起降航班、城际高铁或长途汽车用 Stop.transport，包含 direction、mode、起终点、出发到达时间，以及用户提供的班次、车厢、座位、航站楼、检票口、停止检票时间。不要把高铁伪装为 drive 或 transit。现有模板不提供通用高铁 URI 自动导航；保留清晰的城际信息卡片。

到达当天把往返信息放在第一张卡片；离开当天放最后一张。留宿时最后写回酒店休息；第二天从酒店出发的本地通勤仍要单独填写。

## 7. 地图与导航：复用配置，交接内容

高德代码和代理代码保存在 GitHub，部署在现有 Cloudflare Worker。客户端的公开 JS API Key 与代理地址在构建时使用，服务端安全码通过 Worker Secret `AMAP_SECURITY_JS_CODE` 读取。不要把安全码、Cloudflare Token 或其他密码放进 JSON、MD、HTML 或代码包。沿用当前项目发布无需每次重新设置地图；换账号/域名才另行处理配置。

地图使用实际 GCJ02 坐标。未知坐标直接省略，不能用酒店/区域坐标代替餐馆，也不能把 WGS84 当作 GCJ02。坐标可写已知坐标系，但当前高德不显示未转换的其他坐标系；转换应在资料阶段明确完成。

机场/车站地点可以标记，Stop.mapOverview=false 防止拉远默认取景；机场/车站接驳 leg.mapDisplay=text-only，不画线也不发线路查询。自由逛吃没有固定路线，也用 text-only，不把候选餐馆连成必去路径。返酒店路线可 includeInOverview=false，单独查看。

地图实际道路/步行/公交路径由网页高德服务查询。交接不需要伪造 geometry，也不需要静态直线连点；此前旧导出的 geometry:null 不是此格式的必需字段。网页查询可能重算方案，所以已定线路文字必须保留，不能把实时结果当作自动修改行程的授权。

“地图APP打开 📍”是位置入口，ExternalLink.action=location，用实际 POI 或标记 URL，不默认从当前位置出发。路线“高德地图导航”带明确起终点及已定方式；walk、transit、drive、cycle 在资料齐全时自动映射。taxi、指定途经点或特殊策略需交接有效 navigationUrl；缺少入口不猜，也不默认改成驾车。不要新添 current-location 导航给地点卡片。

## 8. 餐饮分区与采集要求

以酒店、重点景点等为 anchorPlaceId 创建餐饮分区，title 简洁，例如“酒店附近”。原则上每区找至少五家、距离锚点一公里内、大众点评四星以上或有明确高人气依据的候选，记录 cuisine、点评来源、核查时间和门店链接。不足五家时说明真实缺口；不要造评分、距离或商家来凑数。当前长沙参考只有部分区域四家，不能把参考不足当成以后标准。

距离记录 meters、kind、originPlaceId、source、checkedAt，明确直线/步行/驾车，不能把不同口径当成一样。评分记录平台、分值、满分、核查时间，建议同时提供 sourceUrl；无评分不显示评分栏，不填0。

每家尽量提供大众点评、美团的精确门店链接。美团没有门店链接时当前模板用店名搜索入口，按钮仍简写“美团”，不声称搜索页是准确门店；搜索关键词继续使用完整名称与分店。

按钮顺序为“大众点评、美团、地图APP打开 📍、在地图看”。没有正确位置时，不伪造地图按钮目标。地图餐饮小点显式开启餐饮图层即出现，名称在放大后显示；列表定位会放大到可读名称的程度。

当前模板按区域标签切换并显示该区域全部候选。initialVisible 字段保留兼容，但当前没有按它隐藏条目；不要在手册中承诺仅显示前五家。

## 9. 购票、预约与关键时间

PracticalFact 用于 opening、ticket、booking，包含 text、sourceIds、status，可写 checkedAt；元数据保留在 JSON 中，不在网页向同行人展示。

openingMilestones 只填实际查到的停止售票、停止入场、闭馆等 time 与 label。免费预约场所也要查预约和截止时间，不能因为免费省略预约信息。

购票链接使用 platform 为美团/飞猪/携程，action=booking、targetType=detail。当前景点有 ticket 信息且有该平台实际购票链接时，卡片下方显示紧凑购票按钮。某个平台没有入口就不显示该平台按钮；不会为了凑三家而链接平台首页或搜索页。攻略、官网预约是另一个功能，不混成买票。

## 10. 探索候选也用完整景点资料

先广泛收集可去候选，再与用户确定哪些进入日程；未选入但仍值得去的地点放相关日期 nearbyPlaceIds。用户明确不感兴趣、排除的地点不要混入候选。Place 资料与正式景点共用，不另建一个缺少开放/预约等信息的简化格式。

为探索地点同样查简介、位置、适用实用信息、地图和攻略入口，并找一张代表图，放 photos 的第一张。网页下面探索列表默认收起，展开后右侧缩略图112×84px；缺图或图片失败恢复文字布局。

探索候选不进入主时间线、主路线或默认取景。只有开启“探索”或主动点击该候选定位才显示；切换日期恢复图层关闭。共有的路线计算端点也不能绕过这个开关。

## 11. 每日头图、主题色和题诗

每天选一张与该日代表性景点、旅行氛围对应的网上头图 URL，不要求 AI 生图，也不要求图片附件。Day.visual.headerImage 写 src、alt，可选 focalPoint 的 x/y 百分比0–100，默认50/50。内部来源记入 trip.sources（例如 source-day-1-header），不显示到页头。

头图固定高度：手机<768px为192px；平板768–1023px为208px；桌面≥1024px为224px。横图建议1920×960或接近比例，有清晰中央主体，网页 cover 自动裁切，不把标题烘焙进图片。每个日期高度相同。themeColor 是六位十六进制主题色，从该日图/地点选择；缺失则轮换青绿、紫、暖棕、蓝，标签和页头对应。

题诗由规划阶段 AI 生成，按天数逐日提供：四天四首，结合旅行目的、意境、季节和当天确认的地点；浪漫主义、唯美、轻盈，有画面与情绪。优先四句五至七字，或2–4行短自由诗，每行建议不超过14字。写入 Day.visual.poem.lines，每个数组元素一行，不含提示词、解释或署名。不能用同一首重复填所有天；未定方案不胡编当天经历。

图片缺失用纯色，诗缺失或lines为空留白。当天诗、图、色调随日期一起切换，不借用上一天内容。页头只放旅行标题、中文总天数、整趟起止日期和诗，不放当天酒店/车站路线；路线在下方概览。

## 12. 固定样式与缺失规则

版式以 template-contract.json 与模板源码为准，发布阶段不自行重新设计。地图工具栏“总览、餐饮点、探索、全屏”；全屏末项变为“退出全屏”，四项一行。地图默认可操作，缩放±保留；等效文字列表默认折叠、小字体。

底部“总览、地图、行程、吃饭”四个浅底色/细边框/8px圆角按钮，14px粗体，最小高度36px。总览回网页顶部而不换日期。酒店返程依然在日程/交通卡片，不单列底栏入口。

缺图片、诗、票价、购票链接、评分、距离等可选字段：隐藏/留空，不新增“待确认”模块。结构引用错误、非法坐标、起终点顺序冲突：指出具体路径，不能猜数据。某段资料不够画图：保留可执行交通正文，跳过该段地图功能，不连假直线。

## 13. 发布前机械检查及当前技术边界

运行 `python3 scripts/validate-travel-handoff.py <资料.json> --require-ready`：Schema校验、全局ID与跨字段引用检查，报告错误路径与地图/资料缺口；只接受 ready 进入实际发布。字段有误返回具体问题，事实核实仍由前期完成。

当前仓库的长沙页使用城市专用原始导出适配器，不能把新的 JSON 随意替换进去就说自动接入。本套标准使用已经应用V5展示字段的规范化 Trip；新旅行需按发布指令导入 `envelope.trip`，注册到 src/trips/index.ts，复用既有模板，不再次经过长沙专用 adapter。这个注册是固定代码操作，不是重新规划。后续可将注册做成通用上传入口，但本次没有宣称已存在该入口。

资料校验通过后构建、浏览器检查、提交现有GitHub仓库并沿用Cloudflare自动部署。部署成功再返回真实链接，不能把本地HTML当成线上成功。现有地图凭据沿用，不向用户索取或打印密码。

本版是可审阅的交接标准第一稿。它锁定当前模板，不会因新资料缺失自动修改样式；将来增加字段或改样式需提升版本并同步更新 Schema、手册和模板代码。
