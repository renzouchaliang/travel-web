# 给 ChatGPT 的旅行规划指令

请读取随附《交接手册.md》、travel-handoff.schema.json 与 template-contract.json。我的目标是全程用手机轻松聊天确定旅行，再只用一份 JSON 交给 Cloud Codex 发布既定模板。

请遵守以下流程：

1. 先了解旅行目的、日期、同行人、节奏、预算、偏好、住宿和往返安排。每次优先聊当前最影响方案的少量问题，不一次列出整张表。
2. 推荐、讨论并维护方案，区分“用户已确认”与“候选建议”。确定每天的地点、访问顺序、时间和交通方式后，再围绕该方案查资料。不要把推荐自动当成用户决定。
3. 分批收集景点的简介、开放/停止入场/闭馆时间、预约、票价、攻略、官网及实际购票链接；交通的明确起终点、GCJ02坐标、线路、方向、上下车、出口、用时与导航入口；城际班次信息由用户确认，未知不编。
4. 按重点区域整理一公里内至少五家符合评分/人气条件的餐饮候选，记录完整门店身份、简洁展示名、菜系、地址、真实评分口径、距离口径和点评/美团链接。查询条件达不到时如实说，不凑数据。
5. 用同一地点资料结构采集更多可去景点。最终纳入路线的写入日程；未纳入但仍值得去的写入探索候选。排除的地点不重新偷偷安排。
6. 图片全部使用可直接加载的网上 URL：正式景点、探索候选首图、每天的代表性头图。检查是否对应地点、可引用且可加载，保留内部来源记录。不生成背景图，不让我上传图片附件。找不到合适图片可以省略。
7. 为每天选择主题色；生成一天一首浪漫、唯美、有当天意境的短诗，结合旅行目的和当天地点，优先四句五至七字。四天四首，分别写入visual.poem.lines，不重复同一首。缺少确定方案的日期先留空。
8. 不同信息归入明确字段：地点Place、访问Stop、本地通勤RouteLeg、城际Stop.transport、餐饮RestaurantGroup、探索nearbyPlaceIds、每日visual。字段使用英文键，旅行正文使用中文。
9. 总结并与我确认方案，报告重要采集缺口。缺失的可选信息省略，不把“待核实/待确定”写入面向同行人的旅行正文；没有信息的日期允许空白。
10. 确认后生成一个可下载的UTF-8 JSON文件，根结构与Schema一致，handoffStatus=ready。新旅行用publishAction=create及新的trip.id；明确更新同一次旅行才用update和原ID。不要输出HTML，不改变模板，不附图片，不把JSON藏在Markdown字符串中；无法输出文件时给纯JSON代码块，明确文件名。

导出前检查ID、地点引用、同日路段顺序、字段类型、URL、坐标系、日期顺序、评分和距离来源。JSON必须能解析，不能有注释、尾逗号或null占位。样例文件是reference，只供格式参考，不复制其中的酒店、坐标、日期、价格或历史事实到新旅行。

不要向我索取高德安全码或Cloudflare密码。地图配置由现有发布环境复用。网页仅调用高德显示实际路径，不负责重新选景点、交通或餐馆。
